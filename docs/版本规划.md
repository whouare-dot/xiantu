# 《仙途》版本规划

> 本文件是项目的**唯一路线图**，持续维护。
> 记录原则：版本目标 → 具体条目 → 验收标准 → 状态。
> 每次迭代结束后回填实际结果与偏差，不做事后美化。

最后更新：2026-09-12

---

## 〇、产品定位与设计支柱

**一句话**：一款纯前端、零依赖、双击即玩的文字修仙放置游戏。

四条支柱（所有设计服从于此，新增需求先对照这四条）：

| 支柱 | 含义 | 反例（做了就是跑偏） |
|---|---|---|
| **离线是资产** | 离线要产出可规划的成果（洞府建成、炉子出丹），不只是"补点修为" | 离线只给一个修为数字 |
| **选择有复利** | 每个选择在几小时后必须能看出差异（流派、洞府投资方向） | 两个选项收益趋同 |
| **文字即画面** | 没有美术预算，文风与文本量就是核心资产 | 用占位符文案 |
| **里程碑有高潮** | 大境界突破、天劫、飞升必须有仪式化演出 | 后台静默算完给个弹窗 |

**难度取向**：轻松为主，深度可挖。默认挂机零负担，但功法流派、洞府规划、宗门选择提供可选的深度。

| 版本 | 主题 | 状态 |

| **V3.0「问宗」** | 宗门系统 + 立场 + 灵兽系统 | ✅ 已交付 |
| **V4.0「轮回」** | 强制轮回 + 真结局 + 道侣 + 血脉 + 世界事件 | ✅ 已交付 |
| **V5.0「世业」** | 本世劫数 + 飞升演出 + 突破分层 + 曲线重调 | ✅ 已交付 |

> **关于编号**：V1.x ~ V6.0 是**公开前的内部开发里程碑**，上表作为开发史保留，不再新增。
> 自 **`v1.0.0`**（首个公开版本）起改用语义化版本，两者的对应关系只有一条：
> **内部 V6.0 = 对外 v1.0.0**。

### 版本号规则（自 v1.0.0 起）

| 位 | 含义 | 判据 |
|---|---|---|
| **major** | 系统性重做 | 存档不兼容，老玩家需迁移或重开 |
| **minor** | 新内容 | 新增系统 / 章节 / 玩法，存档兼容 |
| **patch** | 修复与调参 | 修 bug、调数值、改文案，存档兼容 |

> 存档自身的格式版本是**独立的一套**，定义在 `src/core/state.js` 的 `SAVE_VERSION`，
> 只作迁移判据，与发布版本号无关。

### 已确认的方向决策

| # | 决策 | 定论 | 影响 |
|---|---|---|---|
| 1 | 轮回机制强度 | **飞升后强制轮回** | V4.0 的终局结构：飞升即开启下一世，保留道基点，每世随机天命。鼓励多周目，游戏从"一条线通关"变成"多世积累" |
| 2 | 成就系统 | **纳入规划**（放在 V2.1，横跨现有内容） | 不需要新内容就能立刻给玩家更多目标，是性价比最高的黏性补充 |
| 3 | 宗门数量与倾向 | 主控自定 | 见 V3.0 章节 |
| 4 | 灵兽参战深度 | 主控自定 | 见 V3.0 章节 |

**版本切分的逻辑**：V2.1 先把交互债还清并补上"零成本黏性"（成就），让玩家在 V3.0 开发期间有得玩；
V3.0 做"归属"（宗门、立场、灵兽）；V4.0 做"终局"（强制轮回 + 真结局）；
V5.0 回过头**把轮回本身做厚**——V4.0 交付的是一个结构完整的轮回，但 5 世是同一章的 5 次重复，
V5.0 要让每一世成为独立的一章。
V6.0 补上 V5.0 漏掉的一半：劫数让**每一世不同**，却没有让**新玩家认得路**——
V6.0 把第一世做成遍览世，此后才谈每世不同。

## 二、V2.0「问道」交付记录（已完成）

### 交付内容

- **架构**：原生 ES Module，28 个 JS 模块，零构建、零外部依赖；`tools/serve.py` 起本地服务器
- **系统**：修炼、突破 + 天劫、回合制战斗、功法流派与参悟、炼丹、炼器、洞府（含离线产出）、坊市与拍卖行、奇遇、探险、试炼塔
- **内容**：26 境界 / 36 件装备 / 26 种敌人 / 63 条奇遇 / 17 张丹方 / 20 张图纸 / 34 个内联水墨 SVG
  > 以上为 V2.0 交付时的规模。后续版本的增补见各版本章节（丹方已补至 21 张，奇遇至 69 条）。
- **存档**：可从 demo 1.x 无损迁移（含旧装备名 → 新装备表的一一映射）

### 数值配平（可复现）

| 指标 | 结果 |
|---|---|
| 零加成基准总时长 | 8.08 天 → **V5.0 重调为 12.11 天**（见 §6.9 主体四） |
| 实测通关（地灵根 ×1.8，半优化玩法） | 2 天 1 小时 → **V5.0 重调后 4 天 1 小时** |
| 各境界隐含倍率 | 稳定 4.0×，无漂移 |
| 战斗各档胜率 | 87% – 100% |

### 集成期修复的关键缺陷（记录备查）

这些缺陷单测跑不出来，只有把系统接起来才暴露：

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 战斗 debuff 无层数上限、在当前值上连乘 | 20 回合后玩家攻击力仅剩 8%，对新手的胜率是 0% |
| 2 | 玩家初始 atk 5 打不动任何敌人 | 战斗玩法对新手完全封闭 → 补初始行囊 + 重标定一阶敌人 |
| 3 | 奇遇修为缩放是平方级膨胀 | 渡劫期一次奇遇给 15 亿修为 = 25 个境界的量 |
| 4 | 洞府灵田用浮点累积 | 33% 概率每次离线少收一批灵材 |
| 5 | `trimZero` 吞掉整数尾零 | 所有 0 位小数百分比静默显示错误（气血满值显示成 1%） |
| 6 | tab 按钮每帧重建 | 点击时元素被销毁，点击直接丢失 |
| 7 | 突破失败/连败保底是死代码 | 所有成功率 <100% 的境界恰好都是天劫关口，走的是另一条路径 |
| 8 | `clamp(…, 0.95)` 把"必定成功"压成 95% | 新手第一次突破就可能失败，与数据表意图矛盾 |
| 9 | `启动游戏.bat` 用 LF 换行 + UTF-8 编码 | cmd.exe 把命令切碎；中文显示乱码 |

### 已知限制（V2.1 / V3.0 消化）

- 试炼塔层数、奇遇冷却、探险冷却不持久化，刷新即重置
- 寿元只增不减，未做"寿元耗尽"结算
- 敌人强度在同档位内跨度较大，靠 `tools/balance_combat.mjs` 手工校准
- 窄屏（<820px）断点未在真机验证

## 三、V2.1「正骨」— 体验修复与交互补强

> **主题**：V2.0 把内容做厚了，交互层却欠了债。这一版专门还债，不加新系统。

### 3.1 核心缺陷：面板每秒重建 DOM ⭐ 最高优先级

**现象**（用户反馈 1、3）：
- 上下滚动列表时，每秒被强制弹回顶部（坊市、炼丹界面必现）
- 鼠标悬停在按钮上时，每秒闪烁一次

**根因**：面板用"签名"决定是否重建 DOM，但**倒计时与实时数值被放进了签名里**：

| 面板 | 签名中的每秒变化值 |
|---|---|
| 坊市 | `Math.ceil(aucLeft)` 拍卖行倒计时 |
| 炼丹 / 炼器 | `activeRemain` 炉子倒计时 |
| 洞府 | `sum.upgrade.remaining`、各建筑剩余时间 |
| 试炼塔 | `Math.floor(player.hp)`、`Math.floor(player.mp)` |

签名一变即 `clear(host)` 全量重建 → 滚动条归零、`:hover` 状态丢失。**问题 3 是 bug，不是设计。**

**修复方案（架构级，不是打补丁）**：

把"重建"与"刷新"彻底分离，新增 `src/ui/panel.js` 统一封装：

```
structureSig  —— 只含结构性信息（列表项集合、子标签、解锁状态）→ 变了才重建 DOM
refresh()     —— 每次渲染只更新已有节点的 textContent（倒计时、余额、血量）
```

所有面板改用它。这同时解决三个问题：滚动位置、hover 闪烁、以及每秒重建的性能浪费。

**验收**：坊市/炼丹界面滚动到底部，静置 10 秒仍停在原位；鼠标悬停按钮 10 秒无闪烁；静置时面板 DOM 节点零重建（用 MutationObserver 断言）。

### 3.2 坊市批量购买（用户反馈 2）

- 商品行支持数量选择：`×1 / ×10 / ×100 / 全部`
- 实时显示总价与余额，买不起时禁用并说明差额
- 丹方/图纸类仍为一次性购买（本身不可叠加）

**验收**：一次买 100 个聚气丹，灵石正确扣除、背包数量正确增加、跨品阶（下/中/上品）扣费无负数。

### 3.3 奇遇选项改造（用户反馈 5）

**问题**：选项带 `hint` 提示会剧透；且选项按收益从高到低排列，**每次选第一个几乎收益最高**，探索乐趣归零。

**实测基线**（`node tools/audit_choices.mjs`，61 条有效奇遇）：

| 「第一个选项」的收益排名 | 条数 | 占比 |
|---|---|---|
| 第 1 名（最赚） | 35 | **57.4%** |
| 第 2 名 | 21 | 34.4% |
| 第 3 名（最差） | 5 | 8.2% |

无偏情况下第 1 名应占 33.3%。**偏差确实存在**：第一个选项是最优的概率接近两倍期望，
而落到最差的概率只有 8.2%。玩家"闭眼选第一个"的策略是有效的——这正是要修的。

**方案**：
1. **移除选项提示**：不再展示 `hint` 与风险收益暗示
2. **打乱选项顺序**：每次弹出时用带种子的洗牌重排（同一次奇遇内顺序固定，避免刷新重掷）
3. 保留 `req` 门槛的置灰显示（那是规则约束，不是剧透）

**验收标准**：改动后重跑 `tools/audit_choices.mjs`，"第一个选项排名"分布接近均匀
（第 1 名占比落在 33% ± 10% 区间）。**这是可量化的验收，不靠感觉。**

### 3.4 个人信息页 v1（用户反馈 6）

新增独立标签页，展示当前全部可公开信息：

- **道号与根本**：姓名、境界、灵根、气运、寿元
- **六维属性**：攻击、防御、身法、暴击、悟性、道心、神识（含加成来源明细）
- **立场**：散修 / 正道 / 魔道 / 中立（V2.1 先落地字段与展示，V3.0 接入剧情）
- **师承与宗门**：V2.1 显示"散修"，V3.0 接入宗门后填充
- **修行统计**：突破次数、渡劫次数、战斗胜负、炼丹炼器产出、奇遇经历
- **称号**：由成就解锁获得，可装备，提供小幅加成

### 3.5 成就系统

**定位**：性价比最高的黏性补充——**不需要任何新内容**，就能把已经做完的东西变成目标。

**设计**：
- 成就按类别组织：**修行**（境界/突破/渡劫）、**战斗**（胜场/爬塔/连胜）、**经营**（炼丹/炼器/洞府等级）、**际遇**（奇遇/探险/收集）、**隐秘**（不解锁则不显示，靠玩家自己撞出来）
- 达成即刻弹窗 + 飘字，并在日志留痕
- 部分成就给**永久加成**（属性/灵石），部分给**称号**（可佩戴，提供小幅加成）

**隐藏成就的展示口径（已定）**：
在「隐秘」分类内以 `???` 占位行显示（名字与描述都遮住），而不是完全隐藏。
理由：完全隐藏的话玩家永远不知道有东西可挖，`???` 才能勾起"这里还有什么"的好奇；
但只放在隐秘分类里，不会污染其它分类的可读性。
系统层另导出 `visibleAchievements()`，语义是"未解锁的隐藏项不在内"，供需要严格口径的场合使用。

**数据驱动**：成就定义放 `src/data/achievements.js`，每条含
`{ id, name, desc, category, hidden, check(state), reward }`，
由 `systems/achievement.js` 在关键事件后统一检查，不在各处散落判断。
过程性条件（最长连败、残血翻盘、一回合取胜等）由 achievement.js 订阅
`COMBAT_END` / `REALM_FAIL` / `REALM_BREAK` 自己记计量器，
**不往 combat.js / breakthrough.js 里塞成就相关代码**。

**验收**：见 `tools/test_achievement.mjs`（已通过）。

## 四、V3.0「问宗」— 宗门、立场与灵兽（设计已冻结）

> **主题**：从"孤身散修"到"有归属、有伙伴"。
> 三个系统互补：**宗门**给归属与长线目标，**立场**让选择有代价，**灵兽**给陪伴与养成。

### 4.1 立场系统（先做，它是另外两个的前提）

**三档立场**，决定奇遇分支、商店价格、可加入的宗门：

| 立场 | 获取方式 | 特性 |
|---|---|---|
| **散修** | 初始状态 / 叛宗后 | 无加成，但奇遇不受立场限制，中立 NPC 都愿交易 |
| **正道** | 加入三大宗门之一 | 商店折扣、宗门任务与宝库、正道奇遇分支；魔道奇遇对你更凶险 |
| **邪道** | 特定奇遇中选择"堕入魔道" | 修炼速率与战斗有加成，但渡劫更难、正道 NPC 敌视、部分奇遇关闭 |

**邪道必须有真实取舍**，不能只是"另一套加成"。设计：`修炼 ×1.15、战斗 ×1.10，但天劫难度 +20%、商店价格 ×1.3、无法加入正道宗门`。

### 4.2 宗门系统（用户反馈 7）

**三个宗门**，各对应一条功法流派：

| 宗门 | 流派 | 加成方向 | 专属资源 |
|---|---|---|---|
| **天剑宗** | 剑修 | 攻击、暴击 | 剑修功法、攻击向法宝 |
| **百草谷** | 丹道 | 炼丹成功率与产量、悟性 | 丹方、稀有药材 |
| **磐岳宗** | 体修 | 气血、防御 | 体修功法、防御向法宝 |

**拜入条件**：筑基期后（realmIndex ≥ 9）。**可叛宗**，代价是贡献清零 + 30 分钟立场冷却 + 该宗门永久好感下降。

**职位晋升**（靠贡献）：
`外门弟子 → 内门弟子 → 真传弟子 → 长老 → 宗主`
每级解锁：宝库层数、宗门建筑位、每日俸禄（灵石 + 稀有材料）。

**宗门贡献**来源：
- **宗门任务**：每日轮换（捐材料 / 交丹药 / 打宗门试炼），完成后给贡献
- **宗门战**：见下
- **宗门建筑产出**：部分建筑持续产贡献

**宗门宝库**（用户明确要求）：按职位分层解锁的兑换列表
- 低阶：丹药、材料、灵石
- 中阶：稀有丹方 / 图纸、灵兽蛋
- 高阶：宗门专属功法、称号、法宝
- **贡献是稀缺资源**，兑换要有取舍，不能全都要

**宗门建筑**（用户明确要求）：独立于个人洞府的第二套建筑体系

| 建筑 | 作用 |
|---|---|
| 演武场 | 提升宗门战战力 |
| 丹塔 | 炼丹成功率 / 产量加成 |
| 藏剑阁 | 功法参悟速度加成 |
| 灵兽园 | 灵兽养成速度、资质上限加成 |
| 护宗大阵 | 宗门战防御、减少战败损失 |

**宗门对抗**（用户明确要求）：
- **异步周结算**：与其他宗门（AI）按周对战
- 个人战力 = 职位权重 + 演武场等级 + 个人战斗属性
- 胜方得大量贡献 + 资源；败方损失部分贡献（护宗大阵可减免），**但不掉境界、不掉已解锁内容**
- 战斗中播放文字战报，让抽象的"宗门战"有画面

### 4.3 灵兽系统（用户反馈 4）

| 环节 | 设计 |
|---|---|
| **获取** | 秘境捕捉（探险触发）、宗门宝库兑换、奇遇偶得、**灵兽蛋**（可离线孵化） |
| **资质** | 1~5 星，决定成长上限，**随机不可改**——这是"无尽追求"的来源 |
| **养成** | 等级（战斗获经验）、亲密度（0~100，影响协战触发率与技能解锁） |
| **进化** | 达到等级 + 消耗同源灵兽或特定材料 → 进阶；形态改名、技能升级、资质上限提升 |
| **参战** | **完整的第二行动单位**：独立行动条、1~2 个技能、气血归零则退场（不死亡，战后恢复） |
| **协战** | 亲密度达标解锁：追击（玩家攻击后灵兽补刀）、护主（替玩家挡一次致命伤） |

**参战设计要点**：灵兽不是"数值挂件"。它有自己的行动条（按 `spd` 独立推进），
玩家用它做战术选择——带攻击型灵兽速杀、带防御型灵兽磨血。
这要求改造 `combat.js` 的回合循环，是本版本技术风险最高的一块，由主控亲自负责。

#### 集成事故记录：契约声明了，实现却没遵守（同类 bug 一次会话内出现两次）

**事故一（我的）**：`stanceCooldownUntil` 我声明在 `state.player` 下，但 `stance.js`
自己在第 123/142 行读写的是 `state.stanceCooldownUntil`（根层）。
后果特别阴险——`stanceCooldown()` 读到自己写的根层值，**显示"冷却 30 分钟"**，
看起来完全正常；而宗门系统读 `player` 层永远是 0，冷却**实际形同虚设**。
一个文件里两处不一致，测出来的每个数字都对，功能却是坏的。

**事故二（宗门 Agent 的）**：同样把立场写在 `state.stance`（根层），
与契约的 `state.player.stance` 不一致。

**教训**：
1. **契约要在代码里有强制力，不能只写在文档里**。跨模块的状态字段，
   应当由一个模块独占读写（如立场只由 `stance.js` 读写），其它模块一律调它的接口。
   宗门系统现已改为调 `setStance()`，不再直接写字段。
2. **"两个模块各自对同一份状态的一部分有写入权"是危险信号**。
3. 集成测试必须**跨模块读同一个字段**来断言（例如"系统 A 写完，系统 B 读到的对吗"），
   只测单模块会全绿。这次的测试就漏了——修复后才补上。

> 注：`state.sect` 与 `state.beasts` 分别由各自的系统独占，
> 立场则由 `stance.js` 独占，`sect.js` 只调接口。这条规则已写进本文档。


## 五、V4.0「轮回」— 强制轮回、真结局与道侣（设计已冻结）

> **主题**：解决"飞升之后玩什么"，并给整个游戏一个终点。
> 这是最后一个大版本：把"一世通关"变成"多世积累"，最后收束到一个真结局。

### 5.1 已确认的方向决策

| # | 决策 | 定论 |
|---|---|---|
| 1 | 轮回保留量 | **中保留**（保留永久成长，不保留当世资源） |
| 2 | 邪道是否可逆 | **可洗白，但代价重** |
| 3 | 是否有结局 | **有真结局**，达成后进入自由模式 |
| 4 | 音效音乐 | ❌ 不做 |
| 5 | 新手引导 | ✅ 轻量引导 |
| 6 | 移动端适配 | ❌ 不做 |
| 7 | 道侣系统 | ✅ 要做 |
| 8 | 世界事件 | ✅ 做；**按单机形态设计**（见 5.6） |

### 5.2 轮回系统（V4.0 的核心）

**触发**：飞升成仙即**强制**进入轮回，不可拒绝。这是设计上的重要一笔——
玩家不能"赖在仙界"，必须把成果转化为下一世的资本。

**保留 / 不保留（"中保留"的具体切分）**：

| 保留 | 不保留 |
|---|---|
| 道基点、天赋树 | 境界、修为、寿元 |
| 图鉴、成就、称号 | 灵石、丹药、材料 |
| 灵兽**血脉**与羁绊 | 灵兽本体与等级 |
| 道侣羁绊 | 装备、洞府等级 |
| 轮回次数与历史记录 | 宗门职位与贡献 |

**设计意图**：保留的是"知识与人脉"，不保留的是"资产"。
每一世都要重新经营，但**经营得更快**——这才是有意义的轮回，而不是"重开一次"。

**道基点**：按飞升时的综合成就换算，来源包括境界深度、渡劫次数、
宗门职位、灵兽收集度、奇遇经历、成就解锁数。它**不随轮回清零**，是唯一的跨世货币。

**天赋树**：三道分支，用道基点永久解锁
- **修行**（修炼速率、突破成功率、天劫抗性）
- **战伐**（战斗属性、灵兽协同、宗门战战力）
- **机缘**（气运、奇遇品质、产出数量、悟性）

**每世天命**：转世时随机出生条件，增加重玩性
- 灵根档次（可被天赋"夺天造化"保底）
- 天命词条：正面（如"剑骨天成：剑修功法参悟速度 +30%"）与负面（如"经脉淤塞：起步修炼 -20%"）
- 部分天命只在特定世数后出现，制造"这一世不一样"的感觉

**轮回加速保底**：每世的初始修炼速度有"记忆残留"加成，
**保证任何一世都不会比上一世更慢**——否则玩家会感到惩罚而非成长。

### 5.3 真结局

**基调**（已由主控确定）：**飞升不是终点，而是另一重牢笼的门槛**。

多世轮回后逐渐浮现真相：飞升者从未真正"出去"过，仙界是更上一层的樊笼，
历代飞升者都在其中重复着同样的循环。真结局是玩家以多世积累的道基，
**打破这个循环本身**——不是飞得更高，而是问一句"为什么要飞"。

**触发条件**：累计轮回 ≥ 5 世 + 三条天赋支线各点满一条主线 + 集齐若干隐藏线索
（线索散落在轮回后的特殊奇遇中，不轮回就永远遇不到）。

**达成之后**：进入**自由模式**——不再强制轮回，可自由选择转世或留在仙界，
所有内容解锁，轮回变成纯粹的可选玩法。

### 5.4 洗白机制（邪道可逆）

邪道可通过 **「渡心魔劫」** 洗白：一场独立的高难天劫（比同境界天劫更难，
且**不可用丹药代劫**）。渡过则立场回到散修、清除邪道负面、获得"劫后余生"永久加成；
失败则保留邪道身份，且冷却期内不可再试。

设计意图：给"选错了"留一条路，但让这条路本身成为一次有分量的挑战——
而不是一个可以随手点的撤销按钮。

### 5.5 灵兽血脉与道侣

**灵兽血脉**：进化树深化、血脉觉醒（跨形态保留技能）、羁绊技能（与玩家/道侣的组合技）。
补上 V3.0 遗留的 `unlockStage` 门控——至今它"有机制、无实战数据"。

**道侣系统**：见 §5.7（深度待定）。

### 5.6 世界事件（单机形态）

**明确前提**：这是单机游戏，**没有真正的全服**。所以不做"服务器事件"，
改做**按现实时间轮换的全局天象事件**——同一时刻所有玩家会遇到同样的天象，
但各自独立结算，互不影响。这样既有"世界在动"的感觉，又不需要任何服务端。

| 天象 | 效果 |
|---|---|
| **灵气潮汐** | 数小时内全玩家修炼速率提升，鼓励上线挂机 |
| **魔道入侵** | 限时高难战斗事件，击退得大量贡献与战功 |
| **秘境开启** | 限时高产出探索，灵兽捕捉率提升 |
| **天降异宝** | 稀有道具投放窗口 |
| **大道压制** | 负面天象：天劫难度上升，但突破奖励翻倍（风险与机会并存） |

事件按现实时间日程轮换，下次天象与倒计时在界面上可见——
让玩家有"等一等就快到了"的期待。

### 5.7 道侣系统（深度已定：有专属剧情线）

**4~6 位可选道侣**，各有性格、背景与一条**专属剧情线** + 专属奇遇 + 双修加成。

**设计要点**：
- **羁绊跨轮回保留**——这是轮回题材独有的情感锚点。
  转世后道侣不记得你，但你记得她；重复结缘会解锁只有多世才能看到的内容。
  「你又一次走到了她面前，而她已经不认得你」——这是只有这个机制才能写出来的东西。
- 双修加成走**已有系统的加成通道**（修炼速率、战斗属性、天象收益），不新开一套数值体系
- 专属奇遇用 V2.1 已建好的效果 DSL 表达，不写新的解释器
- **不做**多角恋冲突、道德审判之类的内容；基调是"同行"，不是"攻略"

### 5.8 轻量引导

不做过场式教学。做法：
- 开局只开放「修炼」一个标签，随境界推进逐个解锁并弹一条说明
- 每个系统首次进入时给一张可关闭的提示卡（一句话讲清"这东西干什么用"）
- 引导全程不阻塞操作，玩家随时可以跳过

### 5.9 状态契约（V4.0，已冻结）

并行开发的前提是先定死数据结构。三个新字段：

```js
state.reincarnation = {
  count: 0,              // 已轮回次数（第 N 世 = count + 1）
  daoBase: 0,            // 道基点：唯一的跨世货币
  talents: {},           // { [talentId]: level } 天赋树
  fate: null,            // 本世天命 { id, name, desc, effects[], bad }
  history: [],           // 历世记录，供 UI 展示"我走过几世"
  memoryBonus: 1,        // 记忆残留加成（保证不会比上一世更慢）
  endingSeen: false,     // 真结局是否已达成
  freeMode: false,       // 达成结局后进入自由模式
  clues: [],             // 已发现的隐藏线索 id（真结局条件）
};

state.companions = {
  met: [],               // 已结识的道侣 id（跨世保留）
  bond: {},              // { [id]: 羁绊值 }（跨世保留，是真结局与解锁条件的依据）
  active: null,          // 当前道侣 id
  stories: {},           // { [id]: 已完成剧情节点 }（跨世保留）
};

state.codex = {          // 图鉴
  techniques: [], equipped: [], pills: [], materials: [],
  beasts: [], enemies: [], encounters: [],
};
```

**轮回时的保留/清空规则**由 `systems/reincarnation.js` 独占实现，
其它模块一律不得自行清空或保留字段——V3.0 的立场契约事故（见 §4.6）就是因为
两个模块各自对同一份状态有写入权。这条规则这次先立好。

#### 5.10.1 灵兽血脉深化

轮回的规则是「中保留：知识留下，资产不留」。灵兽本体属于资产必须清空——
但清空之后，玩家在灵兽上投入的几十个小时就一笔勾销了，下一世再抓同族，
体验和第一世完全一样。那"轮回"在灵兽这条线上就只是个删除键。

血脉就是这条线的答案：**你记得怎么养它们。**

**文件改动**

| 文件 | 改动 |
|---|---|
| `systems/bloodline.js` | **新建**。血脉表数据形状 + 三级等级 + 全部效果 + 觉醒/忘却 |
| `core/state.js` | `beasts.bloodlines = {}` 进初始档（读档经 `mergeDefaults` 自动补齐） |
| `systems/beast.js` | 五处接入：`levelCap` +5 / `beastStats` 属性倍率 / `createBeast` 初始亲密与等级 / `tameBeast` 捕获率 / `layEgg` 孵化时长 |
| `systems/reincarnation.js` | 改为调用 `bloodline.extractFrom` / `installInto`，**保留决策仍独占在本文件** |
| `ui/panels/beastPanel.js` | 新增「血脉」子页 + 觉醒/忘却交互；血脉状态进 `structure()` 指纹 |
| `ui/panels/reincarnationPanel.js` | `bloodlines` 改从 `bloodline.js` 导入 |

**血脉规则**

| 等级 | 条件 | 效果 |
|---|---|---|
| Lv1 相识 | 养过该物种 | 捕获同族 +15%；同族蛋孵化 −20% |
| Lv2 相知 | 历史最佳 ≥3★ | 再捕获初始亲密 +15；该族等级上限 +5；计入全局共鸣 |
| Lv3 共鸣 | 觉醒（按阶级 3~5 个妖丹/内丹） | 再捕获初始等级 Lv.10；出战该族全属性 +15% |
| 全局 | 每条 Lv2+ 血脉 | 全部灵兽属性 +2%，**上限 +12%** |

觉醒还要求「曾把它培育到进化形态」——不能随手抓一只 3 星就点。

**两个容易写错、已用断言锁死的地方**

1. **取并集，不是覆盖。** 某一世只养了一只 1 星同族时，`bestStar`/`stage` 必须取历史最好值。
   覆盖会让玩家的永久进度**凭空倒退**，而且毫无提示——这是本系统最严重的失败形态。
2. **加成必须真的落到系统上。** 等级上限、属性、捕获率、孵化时长四处都做了
   "按公式反算期望值再比对"的断言，避免出现「算出来一套、生效的是另一套」。

> 实现上有一处刻意的分工：**「轮回时保留什么」的决策权只在 `reincarnation.js`**，
> `bloodline.js` 只提供数据形状与效果函数。这是 §5.9 立的规则，防止出现第二个裁判。

#### 5.10.2 真结局演出

玩家为了走到这里飞升了五次、点满三条道途、集齐三片残痕。这是几十个小时的投入。
如果最后只弹一个「恭喜通关」，就等于告诉玩家：你做的所有事只是为了把三个条件凑齐。

所以写的不是结算画面，是**给整段旅程一个说法**——而且这个说法必须由玩家走过的系统
拼出来，道侣、灵兽、成就每一样都要在戏里被认领一次，否则它不算数。

**文件**

| 文件 | 职责 |
|---|---|
| `data/endingText.js` | 五幕脚本：止 / 残痕·路 / 残痕·人 / 残痕·我 / 终 |
| `ui/endingScene.js` | 播放器：逐幕推进、终章落款、跳过 |
| `ui/modal.js` | 加 `cls` 选项（一行改动，换来整个演出复用弹窗体系） |
| `main.js` | 监听 `EV.ENDING` 播放（放总线上，因为达成路径将来不止一条） |
| `ui/panels/reincarnationPanel.js` | 「已看破循环」处加「重看结局」 |
| `styles/main.css` | `.modal-ending` 演出样式（宣纸底 + 墨色正文 + 朱砂重音） |

**三个设计决定**

1. **复用 `modal.js`，不自造全屏层。** 演出期间必须有东西挡住奇遇，
   而 `isModalOpen()` 的集合由 modal.js 独家维护。另起一套就得手写一遍屏蔽逻辑，
   漏掉的后果是：玩家正读到「轮回是有人把再来一次做成了可以传下去的东西」，
   背后突然弹出一只妖兽问要不要打。实机已验证 `isModalOpen()` 为真。
2. **逐行淡入用 CSS `animation-delay`，不用定时器。** 挂机游戏常被切到后台，
   定时器在后台会被节流甚至冻结，切回来演出会卡在半句上。
3. **按钮在洗完字之前禁用。** 否则玩家的眼睛还在读，手已经点下去了——重音句全部被跳过。

**实测**

| 项 | 结果 |
|---|---|
| 五幕推进 | 一·止 → 二·残痕·路 → 三·残痕·人 → 四·残痕·我 → 五·终，逐幕按钮解禁时间 0 / 6.0 / 6.9 / 10.5 / 6.0 秒 |
| 终章落款 | 取真实状态：历经 5 世 / 道基点 / 道侣羁绊 / 灵兽血脉 / 成就——实机读数全对 |
| 奇遇屏蔽 | 演出期间 `isModalOpen()` 为真 |
| 重看 | 轮回面板「重看结局」→ 演出重新从第一幕播 → 可正常跳过关闭 |
| 幂等 | 重复触发 `triggerEnding()` 安全 |

**脚本完整性做了 14 项断言**（`tools/test_ending.mjs` 的 A 组）。理由：结局只会被看到一次，
坏了很难被发现——没有玩家会为了复现 bug 再飞升五次。其中特意拦了两类**静默失败**：
`cls` 写错会导致某一行不上色（肉眼极难发现），以及整篇写成"恭喜/通关"口吻的结算画面。


**轮回核心实测**（飞升即强制轮回）：

| 项 | 结果 |
|---|---|
| 该清空的 | 境界/修为/灵石/装备/宗门/灵兽本体/材料/统计 —— 逐项断言全过 |
| 该保留的 | 道基点/天赋/图鉴/成就/道侣羁绊/灵兽血脉/历世记录 —— 逐项断言全过 |
| 道基点上限 | 九个维度各自设上限，**"奇遇次数"这类可刷项被排除在结算外** |
| 凶命补偿 | 5 条凶命**全部**带正面补偿（断言强制） |
| 旧存档兼容 | V3 存档缺 `reincarnation`/`companions`/`codex`/`guide` 字段时自动补齐 |

**洗白实测**：道心 20（门槛 25）通过率 20%；道心 80 通过率 85%。
300 次尝试成功 264 / 失败 36，失败平均损失 5 万修为。
**一世只能洗白一次**，且再入魔时该限制生效——否则邪道会退化成"先吃红利、回头再洗"的套利窗口。

**天象轮换确定性**：不用运行时随机，日程 = 固定锚点 → `(now - 锚点) mod 周期` 定位格位。
同一时间戳两次调用必得同一结果；**刷新页面天象不变**——否则玩家会觉得系统不可信。

#### 又一例"两套口径并存"的隐患（已修）

`reincarnation.js` 的真结局判定原本自带一个宽松兜底（"每系投入 ≥8 点"），
而设计写的是"点满一条主线"，天赋系统里也有自己的 `isEndingPathUnlocked()`。
两套口径并存，实际生效的是宽松那套，真结局会比设计松得多。

已改为**调用天赋系统的判定**，规则只留一个出处。
这与 §4.6 记录的立场契约事故是同一类问题：**同一件事有两个裁判，就一定会出现"看起来对、实际不对"**。

#### 面板工具的多形态分派事故（已修 + 已加护栏）

V4.0 验收时发现 **11 个面板集体白屏**，且控制台没有报错。

根因在 `ui/panel.js` 的四个写入工具（`setText` / `setWidth` / `toggleClass` / `setDisabled`）。
它们要同时支持三种调用形态：

| 形态 | 例子 | 出现场景 |
|---|---|---|
| 选择器 | `setText(host, '[data-f="atk"]', 58)` | 最常用 |
| 已取节点 | `setText(host, someEl, 58)` | 列表行内查一次、循环里复用 |
| 纯值 | `setText(el, '条件已足')` | 拿到节点直接写 |

修"非法选择器导致面板中断"时，我给定位函数加了一句"第一个参数是元素就直接返回它"。
这一句把**形态一**也吞掉了：`setText(host, '[data-f="atk"]', 58)` 的目标节点变成了 host 自己，
一句 `textContent = 58` 把整个面板骨架冲成纯文本。
更糟的是它**不抛异常**——`renderAll` 的 try/catch 兜不住静默错误，所以是整片白屏而不是一个报错。

正确判据：**参数个数决定是"纯值"还是"给容器"，第二个参数的类型决定是"选择器"还是"已取节点"。**
另加一条兜底：值形态的首参若不是元素一律返回 null —— 这类工具最坏的失败不是"没生效"，而是"改错了对象"。

已补 `tools/test_panel_utils.mjs`（手写极简 DOM 桩，零依赖）锁死这条不变量：
6 组 20 项断言，其中"★ 三参形态绝不碰 host 骨架"是专门的回归护栏。

## 六、V5.0「世业」— 内容纵深与体验打磨

> **状态：✅ 已交付。**
> 用户已定的两条方向：① **加长通关前、让轮回本身变深**（不做"通关后"的新内容）；
> ② **一个大版本做透**（V5.0 一并交付纵深与打磨）。

### 6.0 先看数据：原来的节奏是什么形状

设计前先把一局拆开量一遍，不凭感觉排版本。

| 观察 | 数据 | 含义 |
|---|---|---|
| 一生的耗时分布 | **渡劫期一项占 34.3%**；尾 4 境（21~24）合计 **78.1%**；前 22 境仅 **30.4%** | 前 22 境是过场，最后是墙 |
| 通关世数 | 5 世 | 每世重爬同一套 26 境 |
| 记忆残留曲线 | 第 2 世 ×1.15 → 第 5 世 ×1.60（上限 ×2.5） | **越走越快，不是越走越厚** |
| 飞升的呈现 | 两行日志 + 强制轮回 | 全局最大的里程碑，只有两行字 |
| 突破的呈现 | 所有境界共用同一套 flash + toast | 小境界与大境界没有区别 |

> ⚠ **勘误（建模阶段发现）**：本节初稿写的是「渡劫期占 45.7%、最后 4 境占 82%」，
> 那是 **needCult 需求占比**，不是**时间占比**。
> 修炼速率随境界增长，两者差别很大：真实耗时占比是 **34.3% / 78.1% / 30.4%**。
> 结论方向不变（尾墙确实存在），但引用的数字必须用耗时口径——玩家花掉的是时间，不是修为。

**结论**：原来的问题不是"内容不够多"，而是**这 5 世是同一章的 5 次重复**。
所以"加长通关前"不能靠垒高那堵墙（那只是让 grind 更长），
要靠**把重复的圈变成不同的章**。

### 6.1 主体一：本世劫数 —— 把圈变成章

**机制**：每一世开局，除天命外另给 1 条**本世劫数**，未了结则**不可飞升**。

| 劫数类 | 例 | 逼玩家做什么 |
|---|---|---|
| 斗法 | 渡劫前击败某强敌 | 去打平时会跳过的高难战斗 |
| 养成 | 将一只灵兽养至指定阶 | 这一世真正投入灵兽线 |
| 经营 | 洞府某建筑至指定等级 | 这一世走经营路线 |
| 交游 | 与某位道侣羁绊至指定值 | 这一世走人际线 |
| 探秘 | 拾得一片大道残痕 | 这一世必须去撞奇遇 |

**为什么这个设计同时满足两条方向**：
- *加长通关前*：多了必做事项，一世的实际时长自然上升
- *轮回变深*：每世条件不同，第 3 世和第 5 世的玩法不一样了

**两条硬约束**（不遵守会毁掉轮回）：
1. **劫数必须可完成，不允许出现"这一世废了"**。抽到做不了的劫数时给一次改派机会，
   而不是让玩家重开一局。
2. **劫数不得与立场冲突**。邪道玩家不应被派一个"拜入正道宗门"的劫数。

### 6.2 主体二：天命升级为"本世路线"

**现状**：13 条天命，效果全是纯数值（修炼 +x%、突破率 +y%）。

**改法**：天命从"被动数值"升级为"**本世的路线倾向**"——
天命决定这一世能接到哪一族专属奇遇/事件，凶命给更极端但更赚的路线。

- 劫数回答"这一世要做什么"，天命回答"这一世该怎么走"
- 两者组合出有辨识度的每世开局，而不是"又掷了一次加成"
- 凶命**仍然必须有正面补偿**（V4.0 已立的断言，V5.0 不得违反）

### 6.3 主体三：飞升演出（打磨，优先级最高）

飞升是玩家每世都会经历的收束点，5 世就是 5 次建立仪式感的机会。
现在它只有两行日志——而设计支柱白纸黑字写着「**里程碑有高潮**」。

- **复用 V4.0 结局演出的既有模式**（`ui/endingScene.js`：分幕 + CSS `animation-delay` 淡入
  + 复用 `modal.js` 以白拿奇遇屏蔽），不另造一套
- 内容与结局演出**基调一致但功能不同**：结局是"讲明白"，飞升是"送走这一世"
- 须体现本世的具体成果（这一世养了什么、走到哪、留下什么）

### 6.4 主体四：突破的层次感

现在所有突破共用一套 flash + toast，小境界和大境界没有区别。

按台阶分级：

| 层级 | 呈现 |
|---|---|
| 小境界（同境内进阶） | 现有轻提示即可 |
| 大境界（跨大境） | 一次短演出，点出这一境的意义 |
| 天劫关口 | 完整演出 |

### 6.5 主体五：数值可读性与既有欠债

| 项 | 做法 |
|---|---|
| 加成来源 | 凡是乘算生效的地方都摊开写清楚（信息页已有雏形，推广） |
| 每日任务轮换 | 现为连续窗口，每天 5 条同类（见 §10）。改跨步取样 |
| 修炼曲线 | 最后 4 境吃掉 82% 时间。**必须用 `balance_sim.py` 建模后调**，不许手调数字 |

> 修炼曲线这条要格外小心：它会动到"零加成通关 8.08 天"这条基线。
> 调之前先建模，调之后重跑基线与 `smoke_session.mjs`。

### 6.10 V5.0 期间发现并修掉的缺陷

| # | 缺陷 | 严重度 | 说明 |
|---|---|---|---|
| 1 | **飞升后永久卡在最高境** | 🔴 致命 | 劫数挡住飞升时境界已到 25，此后再无"下一次突破"能触发飞升检查，玩家做完了也走不掉。**由 `test_duty` 实测抓出**，已在 `breakthrough.tick` 补上自动补飞升 |

### 7.0 动因：一条劫数扛不起"新手指引"

V5.0 的劫数把"重复的圈变成不同的章"这件事做成了，但它**没有承担"带新玩家认路"的职责**。

| 观察 | 数据 | 含义 |
|---|---|---|
| 每世功课量 | 1 条，5 类（斩敌/游历/御兽/营造/参悟） | 一世只被推着走**一个**系统 |
| 覆盖面 | 同上 | **炼丹、炼器、宗门、道侣、试炼塔、坊市、图鉴、成就完全不被触及** |
| 新手认知路径 | 17 个标签页靠 `minRealm` 逐个解锁（`ui/tabs.js:9-27`） | 解锁了也不会点开——**没有理由点开** |
| 现有引导 | `ui/guide.js` 的轻量提示 | 只在玩家**已经点进那个页面**时才出现，是个鸡生蛋问题 |

**结论**：第一世应当是一遍**遍览**——把每个玩法都推到玩家面前做一次；之后才谈"每世不同"。
所以本版本的功课系统分两层：**第一世是固定主线，第二世起才是抽签**。

### 7.2 主体二：第二世起的抽样规则

第 2 世起不再走固定主线，改为每世抽 3 门功课：

1. **抽样池** = 主线 20 门中除去 3 门"仅第一世"的（同行 / 集录 / 立名）+ 余课 8 门 = **25 门**
2. **强制横跨不同类别**（不再出现"三门都是斩敌"）
3. **排除上一世做过的**（沿用 V5.0 的排除逻辑）
4. **邪道玩家跳过宗门两门**；抽完才变立场的，走**改派**（沿用现有的一次机会）

> 为什么"同行 / 集录 / 立名"只留在第一世：它们的进度源（`companions` / `codex` / `achievements`）
> 都是**跨世保留**的——老兵每世开局就已经"认识所有人、收过大半图鉴、解过大半成就"，
> 这几门对他只会越来越难做，最后必然卡死。第一世是干净的（一切从零），所以只放那儿。

### 7.3 主体三：立场感知（灰显而非隐藏）

判定归属：`canDo(功课)` 必须与"做完没有"的判定住在同一个模块（`systems/duty.js`），
不得散到 UI 层——否则又是"一件事两个裁判"。

```
呈现规则（每次渲染重算，不是抽签时定死）：
  池子里全部展示
  canDo() === false → 整行置灰不可点 + 提示
  「邪修之身，正道宗门不纳。渡心魔劫洗去魔性后，方可拜入。」
  不计入「任选 N 项」的可选范围
```

**灰显必须是动态的**：邪道唯一出路是渡心魔劫洗白回散修（`stance.js` 的 `attemptRedemption`），
洗白后这两行要**自动解除灰显**。提示文案顺手把出路指出来——
灰显就从"一堵墙"变成"一条引导"。

**保留灰显、不做替换**：若把不可完成的项直接刷掉，玩家的池子里就永远看不到宗门，
反而回到了"新手不知道有宗门"的老问题。

### 7.5 新增状态契约（待冻结）

**⚠ 全部为破坏性变更，旧档迁移是硬要求（见 7.6）。**

```js
// state.reincarnation —— 跨世保留
duties: [{
  id, kind, target,
  need, progress, done,
  rerolls,        // 改派机会
  assignedGen,    // 指派于第几世
}],
dutyMode: 'full' | 'sampled',   // 第一世 full / 其后 sampled
codexBaseline: 0,               // 轮回那刻的图鉴总条数

// state.stats —— 每世清零

  slain: [], encounters: [], pills: [], forged: [], shopBuy: [],
},

```

**为什么"种类"放 `stats`、快照放 `reincarnation`**：
`stats` 不在轮回保留白名单里，天然每世清零，正合"本世"语义；
而 baseline 存的是"上一世的遗产"，必须跨世，放 `stats` 会被清成 0，
"本世新增"就退化成"总收录"了。

**为什么 `kinds` 合成一个对象而不是 5 个平铺字段**：它们语义同类（本世见过的 id 集合），
一起读、一起迁移更省事。已确认全项目**没有任何代码遍历 `stats` 的键**，
所有访问都是 `state.stats.字段 || 0` 的直接形式，加嵌套对象安全。

**`连捷` 的不回退要求**：`winStreak` 会被任意一场败仗清零（`combat.js:652-655`），
所以"达成 10 连胜"必须依靠 `tickDuty` 的"已了结不回退"保护（`duty.js:207` 已有）
锁住，否则玩家赢到 10 场、再输一场，任务会退回未完成。

### 3.1 专项记录：这条 bug 比表面复杂

**修复方式**：`createPanel` 把「重建结构」与「刷新数值」从模式上分开。所有面板的
`structure()` 里不再出现倒计时与实时血蓝值。

**验证过程中的两个额外发现**（不查到底就会误判修好了没）：

1. **`setText` 用 `textContent` 赋值会替换文本节点**，在 MutationObserver 里记成 `childList`。
   这会让"静置时零重建"的自检永远失败，也会持续制造 DOM 结构变更。
   已改为**优先原地修改 `nodeValue`**（只产生 characterData）。

2. **重建时滚动位置会丢失**。结构性变化确实需要重建，但不该把玩家翻到一半的列表弹回顶部。
   已在 `createPanel` 里统一做滚动位置的捕获与还原。
   注意实现细节：**用稳定的 CSS 类定位，不能用子节点下标**——重建往往正是因为某些区块增删
   （如炉火从"燃烧中"变"空闲"），下标会整体错位；且**布局未完成时 `scrollHeight` 为 0，
   若此时做夹取会把位置夹成 0**，那正是"还原"反而清零的原因。

**实测结果**：

| 场景 | 滚动位移 | childList | 判定 |
|---|---|---|---|
| 炼丹·炉火燃烧期间（倒计时每秒刷新） | 0 px | **0** | ✓ 零重建 |
| 炼丹·炉火完成时（真实结构性重建） | 距底部 150→136 px | 一次重建 | ✓ 位置保住，未弹回顶部 |
| 坊市·拍卖行倒计时期间 | 0 px | **0** | ✓ 零重建 |

> 一个测量教训：**用 mutation 条数判断"重建了几次"会严重误导**。
> 一次 `clear + build` 会产生数十条 childList 记录（每个被替换的节点各一条）。
> 初测把"一次重建"读成了"45 次重建"。判断是否重建应当看**时间分布**与**节点身份**，
> 而不是记录条数。
