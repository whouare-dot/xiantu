# 《仙途》V2.0 架构规范

> 本文件是所有开发者 / Agent 的**唯一接口契约**。修改契约必须先改本文件。

## 0. 技术约束

- **原生 ES Module**，无构建步骤、无 npm 依赖。
- 必须在 **HTTP 协议**下运行（`file://` 会被 CORS 拦截）。统一用 `启动游戏.bat` / `启动游戏.sh` 起本地服务器。
- 目标浏览器：Chrome / Edge 现代版本（支持 ES2022、可选链、`structuredClone`）。
- **零外部资源**：所有图形为内联 SVG 字符串，所有字体走系统字体栈，不发起任何网络请求。

## 2. 状态契约（`core/state.js`）

所有系统读写同一个 `state` 对象。**新增字段必须在 `createInitialState()` 中给出默认值**，否则存档迁移会出问题。

```js
{
  meta: {
    version: '2.0.0',        // 存档版本，迁移用
    createdAt: Number,
    lastTick: Number,         // 上次结算时间戳，离线收益用
    totalPlaytime: Number,    // 累计在线秒数
  },

  player: {
    name: String,
    realmIndex: Number,       // 0..25
    cult: Number,             // 当前境界已积累修为
    hp: Number, maxHp: Number,
    mp: Number, maxMp: Number,
    alive: Boolean,

    base: {                   // 裸属性，不含装备/功法加成
      atk: Number, def: Number, spd: Number,
      crit: Number,           // 暴击率 0..1
      critDmg: Number,        // 暴击倍率，如 1.5
      comprehension: Number,  // 悟性：参悟速度 / 突破成功率
      daoHeart: Number,       // 道心：抗心魔、抗天劫
      spiritSense: Number,    // 神识：探索发现率
      luck: Number,           // 气运 1..100
    },
    spiritRoot: { id, name, mult, desc },
  },

  resources: {
    stones: { low: Number, mid: Number, high: Number },  // 下/中/上品灵石，100:1 兑换
    materials: { [materialId]: Number },
  },

  techniques: {
    known: { [techId]: { level: Number, exp: Number, mastered: Boolean } },
    equipped: [techId, ...],   // 主修槽位，上限由境界决定
  },

  equipment: {
    owned: [ { uid, baseId, quality, level, affixes: [ {id, value} ] } ],
    equipped: { weapon: uid|null, armor: uid|null, treasure: uid|null },
    nextUid: Number,
  },

  consumables: { [pillId]: Number },

  cave: {
    level: Number,
    buildings: { [buildingId]: { level: Number, upgradeEndsAt: Number|null } },
  },

  alchemy: { knownRecipes: [recipeId], auto: Boolean },
  forging: { knownRecipes: [recipeId] },

  combat: {
    towerFloor: Number,
    towerBest: Number,
    winStreak: Number,
  },

  log: [ { t, text, cls, channel } ],   // channel: 'cultivate' | 'battle' | 'system'
  flags: {},                             // 剧情/教程标记
  stats: {                               // 统计，成就与功课用。随轮回清零
    breakthroughs: Number, deaths: Number, kills: Number,   // 注意是 kills 不是 killed
    pillsMade: Number, itemsForged: Number, encounters: Number,
    tribulationsPassed: Number, totalCultGained: Number,
    // V6.0 新增（见 §2.1）：本世"种类"去重集合 + 动作计数
    kinds: { slain: [], encounters: [], pills: [], forged: [], shopBuy: [] },
    equipOps: Number, companionMeets: Number,
  },
}
```

### 2.1 V5.0 本世劫数 → V6.0 本世功课

**V6.0 变更**：由"每世 1 条劫数"扩为"每世多门功课"。
第一世走固定主线（**八幕 20 门必做 + 余课任选 2 项**），第 2 世起每世抽 3 门。
字段由 `reincarnation.duty`（单对象）改为 `reincarnation.duties`（数组）。

```js
state.reincarnation.duties = [{
  id: null,        // 功课 id，对应 data/duties.js 的键
  kind: '',        // 见下方进度模型表
  target: null,    // 目标参数（建筑 id / 功法 id / 品阶等），无参数时为 null
  need: 1,         // 需要达到的数量
  progress: 0,     // 当前进度（由 tickDuty 拉取重算，不自行累加）
  done: false,     // 是否已了结
  rerolls: 1,      // 剩余改派次数（抽到做不了的功课时的出口，不允许玩家被卡死）
  assignedGen: 0,  // 指派时的世数，用于识别跨世残留的脏数据
  act: 0,          // 所属幕（1..8）；0 = 余课池
}]
state.reincarnation.dutyMode = 'full' | 'sampled'  // 第一世 full（八幕主线）/ 其后 sampled（每世抽 3 门）
state.reincarnation.codexBaseline = 0   // 轮回那刻的图鉴总条数（本世增量的基数）
state.reincarnation.achBaseline = 0     // 轮回那刻的成就解锁数
```

**⚠ 全部为破坏性变更，旧档迁移是硬性要求（见 §6）。**

#### 新增统计字段（`state.stats`，随轮回清零）

```js
stats.kinds = {                          // 本世"种类"去重集合（id 数组）
  slain: [], encounters: [], pills: [], forged: [], shopBuy: [],
}
stats.equipOps = 0        // 装备穿脱次数
stats.companionMeets = 0  // 本世结识道侣人数
```

`stats` 不在轮回保留白名单里，天然每世清零，正合"本世"语义。
已确认全项目**没有任何代码遍历 `stats` 的键**（全部是 `state.stats.字段 || 0` 的直接访问），
所以 `kinds` 用嵌套对象是安全的。

`codexBaseline` / `achBaseline` **必须放在跨世保留的 `reincarnation` 里**——
它们存的是"上一世的遗产"。放进 `stats` 会被每世清成 0，
"本世新增"就退化成"总收录"了。

**所有权规则（硬性）**

> **功课的生成、推进、判定、改派、立场准入（`canDo`），独占在 `systems/duty.js`。**
> 其它模块一律不得自行判定功课完成，也不得上报进度。

这是 §5.9 立的「一件事只能有一个裁判」规则的延续（做法同 `bloodline.js`：
能力独立成模块，但保留决策仍归 `reincarnation.js`）。V3.0 的立场契约事故
（两个模块各写一半、显示正确但功能永远是坏的）就是这么来的，跨世系统更不能重蹈。

#### 进度模型：全部拉取，不上报

| kind | 进度来源 | 说明 |
|---|---|---|
| `combat` | `state.stats.kills`（本世战斗胜场） | V5.0 遗留 |
| `explore` | `state.stats.encounters`（本世奇遇次数） | V5.0 遗留 |
| `beast` | `state.beasts.owned` 的数量 / `level` / `stage` | target 区分 |
| `cave` | `state.cave.buildings[id].level` / `cave.level` / 建筑等级合计 | target 区分 |
| `cultivate` | `state.techniques.known` 的门数 / 某门重数 | target 区分 |
| `slayKinds` | `state.stats.kinds.slain`（**本世击败过的敌人 id**） | 种类 |
| `encounterKinds` | `state.stats.kinds.encounters` | 种类 |
| `pillKinds` | `state.stats.kinds.pills`（**本世炼成过的丹方 id**） | 种类 |
| `forgeKinds` | `state.stats.kinds.forged` | 种类 |
| `shopKinds` | `state.stats.kinds.shopBuy` | 种类 |
| `tower` | `state.combat.towerFloor` | |
| `streak` | `state.combat.winStreak` | 见约束 4 |
| `equipQuality` | `state.equipment.owned[].quality` 的最高阶 | |
| `equipOps` | `state.stats.equipOps` | |
| `companionMeets` | `state.stats.companionMeets` | |
| `codexDelta` | `codex` 总条数 − `reincarnation.codexBaseline` | 本世增量 |
| `achDelta` | `achievements.unlocked.length` − `reincarnation.achBaseline` | 本世增量 |

**全部拉取，一条上报路径都不留。** 拉取天然正确：读档、离线、跨世
全都不用额外处理，不存在"事件漏发导致进度永久卡住"这种最难查的 bug。
上报则要求每个可能产生进度的地方都记得调用一次——漏一处就是静默的永久卡关。

#### 五条硬约束

1. **进度源必须在轮回时被重置**（或其基线跨世保存）。
   `companions` / `codex` / `achievements` 这些**跨世保留的绝对值不能直接当进度源**——
   必须走 `stats.kinds` 计数器，或用 baseline 做差。否则老兵一开局就自动完成。

2. **不得与立场冲突**。宗门功课**不得进入必做主线**：
   `canJoin` 硬拒邪道（`sect.js`），设为必做会让邪道玩家永久无法飞升。
   宗门只能放"任选"池，对邪道**灰显 + 指路**（见 §2.1.1），绝不隐藏。

3. **"种类"优先于"数量"**。凡是能表达成"做过 N 种"的，不写成"做过 N 次"——
   后者会被反复刷同一种低级内容冲量（如反复炼聚气丹）。

4. **已了结的功课不回退**。`done` 一旦为真，`progress` 不再回落。
   `winStreak` 会被任意一场败仗清零、灵兽数量会因放生下降，
   这些波动都靠这条兜住——否则玩家达成后又被判回未完成。

5. **旧档必须可迁移**。旧的单条 `duty` 要能塞进 `duties` 数组；
   无 `duty` 的档沿用 V5.0 的"视为已了结"放行（不能把老玩家卡在门外）。

#### 2.1.1 立场准入（V6.0 新增）

`canDo(功课)` 判定某门功课当前立场能否完成，**必须与"做完没有"的判定同住 `duty.js`**，
不得散到 `ui/`：

| 功课类别 | canDo 条件 |
|---|---|
| 宗门类（拜山门 / 晋真传） | `state.player.stance !== 'xiedao'` |
| 其余全部 | 恒 `true` |

**灰显而非隐藏**，且**必须每次渲染重算**（不是抽签时定死）——
邪道唯一出路是渡心魔劫洗白回散修（`stance.js` 的 `attemptRedemption`），
洗白后要**自动解除灰显**。提示文案须指出去路，让灰显从"一堵墙"变成"一条引导"。

#### 2.1.2 "还差什么"的暴露（V6.0 新增）

`dutySummary()` 必须为"种类"型功课给出 **`missing: []`**（尚未达成的那几种），
供 UI 逐条列出。只给标量 `progress/need` 是不够的——
玩家会盯着 `3/6` 却不知道还该去做什么。

## 3. 派生属性（不进存档，每次结算）

`systems/cultivation.js` 导出纯函数，所有加成都在这里汇总，**加成必须叠加而非相乘叠加到失控**：

```js
calcCultSpeed(state) -> Number   // 修为/秒
calcMaxHp(state) / calcMaxMp(state)
calcAtk(state) / calcDef(state) / calcSpd(state)
calcCrit(state) / calcCritDmg(state)
calcBreakChance(state) -> Number // 0.05..0.98
```

公式骨架（`balance_sim.py` 产出系数）：
```
cultSpeed = baseSpeed(realmIndex)
          × rootMult × techniqueMult × caveMult × pillBuff × eventBuff
```

## 4. 事件总线（`core/bus.js`）

系统间通过事件解耦，避免循环依赖。

```js
bus.on('cult:gain', fn)      // 修为增加后
bus.on('realm:break', fn)    // 突破成功
bus.on('realm:fail', fn)     // 突破失败
bus.on('tribulation:start'|'end', fn)
bus.on('combat:end', fn)
bus.on('item:gain'|'item:use', fn)
bus.on('log', fn)            // 任何日志
bus.emit(name, payload)
```

**日志统一走 `bus.emit('log', {text, cls, channel})`**，由 `ui/` 订阅后渲染。`systems/` 里不允许出现 `document.`。

## 5. 日志分级

| cls | 用途 |
|---|---|
| `event-good` | 增益 |
| `event-bad` | 损失 |
| `event-special` | 稀有 / 重要 |
| `event-breakthrough` | 突破（大字演出） |
| `event-tribulation` | 天劫 |
| `event-battle` | 战斗战报 |

`channel` 用于日志分栏：`cultivate`（修行）/ `battle`（战报）/ `system`（系统）。

## 6. 存档与迁移（`core/save.js`）

- `key = 'xiantu_save_v2'`，与旧版 `'xiantu_save'` 隔离。
- `MIGRATIONS = { '1.2.0': fn, ... }`：从旧存档读入时逐级升级。
- **首次启动检测到旧存档 → 自动迁移**（保住老玩家进度），迁移后在日志中说明。
- 注意旧版的 `|| 默认值` 假值陷阱：`0` 是合法值，必须用 `??` 而非 `||`。
- 支持导出/导入（Base64 文本串）与三个存档槽。

## 7. 命名约定

- 数据 id：小写 + 下划线，如 `pill_juqi`、`tech_qingfeng`、`mat_herb_1`。
- 品阶枚举：`fan | ling | xian | shen | sheng`（凡/灵/仙/神/圣），对应 CSS `quality-fan` 等。
- 大境界段：`qi`(炼气) `zhu`(筑基) `jin`(金丹) `yuan`(元婴) `hua`(化神) `xu`(炼虚) `he`(合体) `cheng`(大乘) `jie`(渡劫) `xian`(飞升)。

## 8. 性能与渲染约定

- 主循环 **1 次/秒**，但 **DOM 全量重绘不得超过 4 次/秒**（用脏标记 + 节流）。
- 日志节点上限 200 条，超出丢弃最旧。

### 8.1 面板必须用 `createPanel`（硬性规定）

`src/ui/panel.js` 的 `createPanel({ id, structure, build, refresh })` 是**所有面板的唯一写法**。

```
structure()  只返回「结构性信息」→ 变了才重建 DOM
build(host)  搭骨架，不写任何会变的数值
refresh(host) 每帧调用，只改已有节点的 textContent / width / disabled
```

**`structure()` 里绝对禁止出现**：剩余秒数、`remaining`、实时 hp/mp、`Date.now()`、
余额、任何每秒变化的量。

#### 这条规则是踩过坑写下的

V2.0 的写法是把签名当"是否需要重绘"的判据，但签名里混进了倒计时和血蓝值，
结果坊市、炼丹、炼器、洞府、试炼塔这几个面板**实际上每秒全量重建一次**。玩家的体感是：

1. 列表滚动位置每秒被弹回顶部
2. 鼠标悬停在按钮上时 `:hover` 丢失，**每秒闪一下**

这两个都是玩家直接反馈的 bug。正确做法不是"把倒计时从签名里删掉"，
而是从模式上把「重建」与「刷新」分开——数值变化根本不需要重建 DOM。

#### 配套工具

`setText` / `setWidth` / `setTexts` / `toggleClass` / `setDisabled` / `countdownText`，
都做了"值没变就不碰 DOM"的判断。倒计时一律用 `countdownText(秒)` 统一格式。

#### 自检方法

用 `MutationObserver` 监听面板容器，静置 5 秒；若 `childList` 有变化就说明还在重建。

## 9. 修改流程

1. 先改本文件的契约。
2. 再改 `core/state.js` 的默认值 + `core/save.js` 的迁移。
3. 最后改系统与 UI。

## 10. 数值诊断采集（`core/telemetry.js`）

用途：为"修炼偏慢"这类**体感反馈**提供可核算的实测数据。口径定义见
`设计文档.md` §0，本模块采集的是 P1（纯在线游戏秒）与 P3（玩家交互时长）。

### 硬性约束

| 约束 | 原因 |
|---|---|
| **不得 import 任何 `systems/` 下的模块** | `cultivation.js` 要调用它，反向 import 即成环。需要倍率明细时由 `main.js` 通过 `initTelemetry({ getBreakdown })` 注入 |
| **不写主存档**，用独立的 `xiantu_telemetry` key | 避免撑大 `xiantu_v2_slot*`，也不必动 `createInitialState` 的迁移契约 |
| **所有公开入口 try/catch 包住，永不抛错** | 诊断工具把游戏搞崩比没有更糟 |
| **只记事件与小时聚合，不记 tick 快照** | 一局 100 小时按 1Hz 快照是 36 万条，无法阅读；事件日志约 1000 条 |

### 数据的来源方式

- **修为来源用 push**：`gainCult` 是全部修为增量的**唯一出口**，来源标签在那里打一次，
  各发奖点只传 `source`。新增发奖点若忘了传，会落到「未知」——摘要里一眼可见。
- **修为扣减也是 push**，但扣减不走 `gainCult`（直接改 `state.player.cult`），
  所以突破 / 天劫 / 洗白 / 负面奇遇这四处需要**显式调用** `noteCultLoss`。
- **境界变化与停留时长用 pull**：每秒轮询 `realmIndex`。改境界的路径有多条，
  轮询漏不掉，比逐个埋点稳。

### 自检

`selfCheck()` 核对「按来源拆分的增量之和」是否**精确等于** `stats.totalCultGained` 的增量。
因为 `gainCult` 是唯一增量出口，不等就说明有并行路径或重复计数。
`tools/test_telemetry.mjs` 有断言守着。

**已知的跨会话缺口**：游戏自动存档是 30s 一次、采集落盘是 60s 一次，两个节拍不同，
刷新页面会丢掉尾段（实测一次约 47 秒的修炼量）。这不是漏采，处理方式是
`initTelemetry` 里把它折进基线并记入 `meta.crossSessionDrift`，摘要中显式列出。

### 导出

设置页「数值诊断」区：导出 JSON（完整事件）/ 复制摘要（给人看，可直接贴回对话）/ 清空。
